# 三设备同步钢琴录音基准结论

日期：2026-10-19

数据依据：iPhone、iPad、Mac 同步录制同一段钢琴演奏的三份完整 JSON 导出；每份含第一遍较慢、第二遍较快两轮录音。以下设备映射由用户确认，并与导出中的设备名、User-Agent 交叉核对。

## 设备识别

| 文件                                          | 设备归属           | 导出设备/浏览器信息                     | 备注                                                                              |
| --------------------------------------------- | ------------------ | --------------------------------------- | --------------------------------------------------------------------------------- |
| `iphone-safari-2026-10-19_18-01-47.json`      | iOS 手机（iPhone） | iPhone 麦克风 · Safari · iPhone OS 18.7 | UA 明确为 iPhone                                                                  |
| `ipad-safari-2026-10-19_18-03-09.json`        | iPad               | iPad 麦克风 · Safari                    | iPadOS Safari 使用桌面式 UA，报告显示 MacIntel；按用户说明及输入设备名判定为 iPad |
| `macbook-pro-chrome-2026-10-19_18-03-36.json` | Mac                | MacBook Pro 内置麦克风 · Chrome 153     | UA 显示 macOS/Chrome                                                              |

文件名时间使用北京时间（UTC+8），格式为 `YYYY-MM-DD_HH-mm-ss`；原始导出时间和数据内容保持不变。

三份数据均为 48 kHz。第一遍持续约 65.5–73.0 秒，第二遍约 37.2–43.9 秒，符合第一遍较慢、第二遍较快的描述；这些时长也包含设备端录制起止时间差，不能当作纯演奏计时。

## 主要结果

每份 JSON 包含两种算法、两遍录音和每算法 648 组参数，共 2,592 条评估。下表列出各轮 SwiftF0 扫描中达到的最高正确数；YIN 的最高正确数作为算法对照。完全相同的旋钮组合在不同设备/速度下结果不同，因此这些“最高值”是各自扫描上限，不是统一推荐配置。

| 设备   | 第一遍较慢：SwiftF0 最高 | YIN 最高 | 第二遍较快：SwiftF0 最高 | YIN 最高 |
| ------ | -----------------------: | -------: | -----------------------: | -------: |
| iPhone |  60/60（324 组配置达到） |    55/60 |          59/60（114 组） |    28/60 |
| iPad   |           60/60（19 组） |    55/60 |           59/60（58 组） |    35/60 |
| Mac    |          59/60（207 组） |    43/60 |            44/60（3 组） |     5/60 |

三台设备上 SwiftF0 都优于 YIN。较快的一遍对 Mac 的离线识别明显更难：SwiftF0 扫描中最高也只有 44/60；iPhone 和 iPad 的最高结果均为 59/60。在此次扫描覆盖的参数范围内，没有组合让 Mac 快速录音追到移动端结果。

## 旧参数组合与当前参数组合

逐设备对照两个组合：历史高敏感组合（SwiftF0、30 ms、置信度 0.4、RMS 0.0009、2 稳定帧、50 ms）与当前组合（SwiftF0、40 ms、置信度 0.7、RMS 0.0009、3 稳定帧、80 ms）。每格顺序是正确/错音/漏音/额外报音。分析增益固定为各设备录音时的值，因此并非相同增益条件下的硬件对比。

| 设备   | 演奏轮次 | 历史组合  | 当前组合  |
| ------ | -------- | --------- | --------- |
| iPhone | 慢       | 60/0/0/0  | 59/1/0/1  |
| iPhone | 快       | 59/1/0/1  | 55/2/3/1  |
| iPad   | 慢       | 60/0/0/4  | 53/1/6/0  |
| iPad   | 快       | 59/1/0/1  | 53/0/7/0  |
| Mac    | 慢       | 59/1/0/4  | 57/1/2/2  |
| Mac    | 快       | 43/6/11/4 | 25/1/34/0 |

较低置信度、较短帧间隔和更宽松的稳定门槛，在 iPhone/iPad 录音上找回更多目标音；同时 iPad 慢速轮次多出 4 个额外报音。Mac 快速轮次的历史组合从 25 个正确提高到 43 个，但仍漏 11 音、错 6 音、额外报 4 音；全矩阵最高也只有 44/60。第二遍 Mac 在当前组合下漏掉 G5（MIDI 79）；iPhone 和 iPad 的第二遍当前组合未漏掉 G5。结果支持把历史组合纳入后续实时对照测试，不足以直接回退全局默认值。

## 设备输入差异

| 设备   | 敏感度档位 | 分析增益 | 原始 RMS（慢 / 快） | 放大后削波比例（慢 / 快） |
| ------ | ---------: | -------: | ------------------: | ------------------------: |
| iPhone |          3 |      15× |   0.00337 / 0.00437 |        0.0013% / 0.00056% |
| iPad   |          3 |      15× | 0.000405 / 0.000526 |                     0 / 0 |
| Mac    |          2 |       8× |   0.03330 / 0.04680 |             1.04% / 2.15% |

Mac 的输入 RMS 显著高于另外两台，增益与敏感度档位也不同；应用分析增益后，Mac 音频出现较多削波样本，尤其是较快一遍。该现象与 Mac 快速录音的低命中同时出现，是需要优先排查的输入链路差异，但仅凭这组对照不能证明削波是唯一原因。iPad 的原始 RMS 最低，却在 SwiftF0 扫描的最佳配置下达到 59–60/60，说明不能只根据原始 RMS 大小判断可识别性。

## 参数趋势（SwiftF0）

以下是每个参数档位在其余参数组合上的平均正确数，反映本轮数据中的总体趋势；参数之间存在交互，不能视为单变量因果实验或直接当作推荐值。

评分口径需注意：`extra` 是把识别出的 MIDI 音高序列与 60 个目标音序列做编辑距离匹配后得到的“插入”数；此步骤不使用起音时间标记。起音标记只用于为已匹配的正确音估算延迟，而且自动 RMS 标记可能多检瞬态或漏掉连奏音。每个参数结果只保存汇总计数，没有保存该组合全部预测事件的时间与音高。因此这里的 `extra` 不能单独证明是现场噪声误报，也不能仅凭结果摘要把它对应到某个具体起音标记；要判断具体原因，需要重新跑该组合并保留事件级输出，结合原始录音和标记核查。

针对 Mac 候选（置信度 0.4、50 ms、低 RMS、2 帧、50 ms），已从归档分析 WAV 重跑事件级识别；正确、错音、漏音、额外计数与原 JSON 完全一致。四个慢速轮次额外事件发生在 44.210s（MIDI 39，目标序列第 37 个音前）、44.460s（MIDI 92，第 37 个音前）、47.160s（MIDI 46，第 40 个音前）、50.710s（MIDI 42，第 44 个音前）。快速轮次两个额外事件发生在 7.160s（MIDI 48，第二个目标音前）和 25.110s（MIDI 95，第 35 个目标音前）。因此没有一个出现在演奏尾部；快速轮次有一个靠近开头，其余都在中段。快速轮次 7.160s 的事件与自动起音标记 7.155s 几乎重合，说明它不应未经核听就称作纯噪声误报；它可能是该起音处音高被额外/错误识别。其余事件也需结合音频逐个核听，序列位置本身不能确定成因。

| iPad 参数档位 | 慢速轮次平均正确数 | 快速轮次平均正确数 |
| ------------- | -----------------: | -----------------: |
| 置信度 0.4    |              57.27 |              57.37 |
| 置信度 0.5    |              55.69 |              56.36 |
| 置信度 0.6    |              53.38 |              53.20 |
| 置信度 0.7    |              51.36 |              49.85 |
| 置信度 0.8    |              44.85 |              42.79 |
| 置信度 0.9    |              30.52 |              20.11 |

iPad 上置信度门槛是最明显的趋势：从 0.4 提高到 0.7，跨其余设置平均少命中约 6–8 音；0.9 时下降更明显。取样间隔从 50 ms 缩短到 20 ms 也整体改善快速轮次（平均正确数 42.54 → 49.39），但效果小于置信度档位差异。Mac 快速轮次也有类似置信度趋势（0.4 平均 36.58，0.7 平均 23.92），但所有参数组合最高仍只有 44/60，说明单靠降低门槛不能消除异常。

这轮数据没有复现“iPad 当前配置识别不到 G5（MIDI 79）”：第二遍 iPad 当前参数下 G5 有命中；但同一当前组合整轮仍为 53/60，漏掉其他 7 个音。因而可以说当前门槛可能造成整体漏音，不能据这段离线数据认定 G5 本身的实时识别故障已定位或已排除。

若要选一个下一轮 iPad 实时 A/B 候选，可先试：SwiftF0、置信度 0.4、20 ms、低 RMS 门槛（0.0009）、2 稳定帧、最短稳定时间 65 ms。该组合在本次两遍回放分别为 60/60（2 个额外报音）和 59/60（1 个错音、无漏音或额外报音），合计 119/120 正确；当前组合合计 106/120 正确且漏 13 音。这个结果只覆盖本次两遍录音，属于候选而非默认值结论。相较当前 40 ms，20 ms 的取样频率约翻倍；扫描中单次 Worker 处理时间约 0.8–1.5 ms，但实时电量、热量和长时间负载仍需在 iPad 验证。降低置信度与稳定门槛也可能让环境噪声或短暂泛音触发误报。

## 配置建议与观测代价

按每台设备两遍合计（120 个目标音）比较，下面的候选是在这次扫描中表现较好的方向。计数格式仍为正确 / 错音 / 漏音 / 额外序列事件；“额外”是评分器插入数，不等于已经人工确认的噪声误报。

| 设备   | 当前组合：0.7 / 40 ms / 3 帧 / 80 ms |         本轮候选 | 候选组合                   | 取舍                                           |
| ------ | -----------------------------------: | ---------------: | -------------------------- | ---------------------------------------------- |
| iPhone |                      114 / 3 / 3 / 2 |  119 / 1 / 0 / 0 | 0.4 / 40 ms / 2 帧 / 50 ms | 少漏 3、少错 2；本次无额外序列事件             |
| iPad   |                     106 / 1 / 13 / 0 |  119 / 1 / 0 / 2 | 0.4 / 20 ms / 2 帧 / 65 ms | 少漏 13；多 2 个额外序列事件，采样频率约翻倍   |
| Mac    |                      82 / 2 / 36 / 2 | 103 / 6 / 11 / 6 | 0.4 / 50 ms / 2 帧 / 50 ms | 少漏 25；多 4 错音、4 个额外序列事件，取样较慢 |

表中三个候选均使用低 RMS 门槛 0.0009。iPhone 与 iPad 的数据支持降低置信度并减少稳定帧；iPad 候选进一步用 20 ms 提高弱音捕获。Mac 即使选到本次扫描中总体计数较好的组合，快速轮次仍有 11 个漏音和 5 个错音；不建议把算法阈值当作 Mac 的完整解决方案。这个三端对比来自一段演奏，适合决定下一轮 A/B 方向，不足以单凭它发布按设备的默认阈值。

如果必须先选一个三端共用的平衡候选，本轮 648 组组合中，SwiftF0、置信度 0.4、40 ms、RMS 中门槛（0.0018）、2 稳定帧、50 ms 的三端合计为 333 正确、10 错音、17 漏音、4 个额外序列事件。当前组合合计为 302 / 6 / 52 / 4：候选少漏 35 音、额外事件数相同，但多 4 个错音。更偏向少漏音的历史组合（0.4 / 30 ms / RMS 低 / 2 帧 / 50 ms）为 340 / 9 / 11 / 14：比平衡候选多识别 7 个目标音、少 6 个漏音，但多 10 个额外序列事件。这里按错音、漏音、插入各计 1 的总量选候选；真实产品代价权重尚未定义，且“额外序列事件”未核实为真实噪声误报，所以应把这两组作为实时 A/B 选项，而非最终默认值。

## 结论与边界

1. 新的三设备同步录音替代 2026-10-18 单 Mac 数据，作为当前跨设备比较依据；旧报告中的“恢复旧参数会增加误报”等结论不再代表本轮结果。
2. iPhone 与 iPad 的 SwiftF0 在两种速度下均有接近完整的参数组合；当前较严格配置在 iPad 两遍都只识别 53/60。iPad 参数边际趋势指向置信度门槛过高是主要可调因素，但 G5 未在当前离线配置下漏识别，因此用户报告的特定音高问题仍需实时复测。
3. Mac 的快速录音是主要异常点。Mac 与移动设备的敏感度和增益不一致，且存在明显的增益后削波；先确认 Mac 的输入增益/麦克风电平和录音是否过载，再判断是否需要调整算法阈值。
4. 本结果来自离线录音回放与目标音序评分，不等价于实时练习端到端表现；不能将三个设备的最佳参数分别直接写回产品默认值。最终调整仍需在每台设备上实时验证。
